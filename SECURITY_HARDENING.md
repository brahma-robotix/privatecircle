# PrivateCircle security hardening

This change is a security patch proposal. It is not active in the hosted Supabase project until the SQL is reviewed and applied, and the application branch is deployed.

## What changed

- Restricts direct profile reads to the account owner and active admins.
- Adds a limited circle directory view and a consent-filtered location view.
- Revokes direct updates to privileged profile columns; admin role/status changes use a database-checked RPC.
- Removes public invitation-row reads. Invitation verification returns only a boolean.
- Makes invitation claiming atomic in the Auth user trigger and binds invitations to the signup email.
- Replaces first-user automatic admin promotion with a one-time, email-bound bootstrap token generated by the database owner.
- Prevents joining arbitrary existing conversations by guessing IDs.
- Restricts attachment object reads to conversation participants.
- Prevents Supabase-mode demo login and stops persisting Supabase-mode conversations/private state in localStorage.
- Uses cryptographically secure random invitation codes.

## Apply safely

1. Back up the database and test this patch in a separate Supabase project first.
2. Apply the base schema and numbered chunks in the project's documented order, then apply `supabase/chunks/15-security-hardening.sql`.
3. For a brand-new project with zero profiles, run this in Supabase SQL Editor as the database owner, replacing the address with the intended administrator email:

   ```sql
   SELECT private.create_admin_bootstrap_token('admin@example.com');
   ```

4. Copy the returned token once and enter it in the app's invitation-code field while signing up with that exact email. The token is single-use and should be treated like a password. Do not commit it or share it in chat.
5. For an existing project, do not run the bootstrap-token step if profiles already exist. Verify which account should be the first admin and, if no admin exists, promote the intended verified account manually from the Supabase SQL Editor as the database owner.
6. Deploy the code from this branch only after reviewing the pull request and applying the migration to staging.
7. Verify using two separate accounts: a normal member must not read other profiles' emails or settings, change roles/status, read another conversation's attachments, or join a conversation they were not invited to. Confirm the admin can still manage invitations and roles.
8. Run the Supabase security advisors and review database policies and storage policies after applying. Do not treat a successful frontend build as proof that RLS is secure.

## Important limitations to validate before production

- The location view enforces database-side consent filtering, but the UI must be updated to read `shared_locations` for cross-device partner-location display. Do not assume the location UI is fully integrated merely because the view exists.
- The attachment read policy expects `public.attachments.file_path` to store the exact Storage object path, not a full signed URL. Verify upload/download code uses object paths; otherwise adapt the policy and service before enabling it.
- Translation providers, real-time subscriptions, session revocation, rate limits, and external API integrations require separate tests.
- This patch has not been run against the live database. Never apply directly to production without staging verification and a backup.
